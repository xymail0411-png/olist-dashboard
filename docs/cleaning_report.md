# 数据治理报告

> 阶段：数据入库 → 数据治理 ｜ 脚本：`scripts/02_clean.py` ｜ 数据源：MySQL `olist` 库 ｜ 产出：`data/processed/`

## 治理目标

把 MySQL 原始表清洗为"分析用干净数据"，并明确所有指标口径，保证后续 EDA、建模、可视化共用同一份可信数据。

## 治理口径

| 口径 | 定义 | 原因 |
|---|---|---|
| 有效订单 | `order_status == 'delivered'` | 非 delivered（canceled 等）订单未完成交易，计入会污染收入与时效指标 |
| 用户 | `customer_unique_id` | 同一人多次下单生成多个 customer_id，用户级分析必须按 unique_id 去重 |
| GMV | 订单明细 `price + freight_value` 求和 | 一单多支付会重复计，明细求和才是商品实际成交额 |
| 缺失类目 | 归入 `'unknown'` | 保留商品样本，分析品类结构时单列 unknown 类目 |
| 地理范围 | 巴西经纬度 (lat -35~6, lng -75~-30) | geolocation 含非巴西离群坐标，地图可视化前必须过滤 |

## 执行结果

| # | 规则 | 结果 | 解读 |
|---|---|---|---|
| 1 | 有效订单过滤 | delivered **96,478** / 全部 99,441，排除 2,963 单 | 分析的基准 N 为 96,478 单 |
| 2 | 订单金额（明细求和） | 98,666 单有明细 | **非 delivered 订单也有商品明细**——先过滤状态再算金额，避免取消单计入 GMV |
| 3 | 评论聚合 | 98,673 单有评分（覆盖率 99.2%）| 评论数据完整，星级分析可信度高 |
| 4 | 履约时效 | 超时 **7,307** / 96,478（7.6%）| 92.4% 准时交付；7.6% 超时单是履约分析的重点对象 |
| 5 | 订单主宽表 | 96,478 行 × 17 列 → `orders_master.csv` | 后续 EDA/建模/Tableau 的唯一订单级数据源 |
| 6 | 商品类目 | 610 个缺失 → `'unknown'`，共 32,951 个商品 | 1.9% 商品无类目，单列处理 |
| 7 | 地理过滤 | 保留 1,000,134 / 1,000,163，排除 29 个离群坐标 | 官方数据质量高，离群占比极小 |

## 产出文件

- `data/processed/orders_master.csv`：订单主宽表（订单维度，含客户/金额/时效/评分/支付）
- `data/processed/products_clean.csv`：商品表（类目已翻译 + 缺失归 unknown）
- `data/processed/geolocation_br.csv`：巴西范围内地理位置表（地图可视化用）

## 可改进点

- 超时订单的深层归因（州/品类/卖家维度）留待 EDA 与履约模块深挖
- 取消订单的明细数据可单独分析（取消原因可能与商品/卖家相关）
